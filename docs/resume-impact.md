# Resume impact report

Every number below comes from a file in this repository and can be reproduced with the
command next to it. All workloads are **synthetic**, generated by
`benchmarks/generate.py` or `samples/`. **Facet has no production users, traffic or
adoption metrics, and none are claimed.** Benchmarks ran on one shared 4-vCPU cloud VM
(Intel Xeon @ 2.10 GHz, 15.7 GiB RAM), with the API, worker, PostgreSQL and the load
generator all on that machine.

## Resume bullets

- **Built Facet, a full-stack SQL analytics platform** (FastAPI, DuckDB, PostgreSQL,
  Next.js and TypeScript): CSV and Parquet upload, schema inference, profiling, a SQL
  editor, charts and drag-and-drop dashboards. It runs with one `docker compose up` and is
  covered by 181 backend tests, 16 frontend unit tests and a Playwright end-to-end test of
  the full upload-to-dashboard workflow.
- **Designed a sandbox for untrusted SQL** with three independent layers: a sqlglot AST
  allowlist that re-renders validated queries, a locked-down DuckDB connection per query,
  and a forkserver process pool with time, memory and concurrency limits. It blocks 47
  attack queries, including file, URL and extension access, and costs about 17 ms of
  setup per query.
- **Engineered a streaming ingest pipeline** on a PostgreSQL `SKIP LOCKED` job queue with
  leases, heartbeats and crash recovery. It converts a 5M-row, 438 MiB CSV to Parquet in
  2.2 s of worker time (2.27M rows/s) with no measurable API memory growth. Storing
  Parquet made aggregate queries 13× faster than scanning the CSV.

## Architecture in two minutes

The API (FastAPI) owns HTTP, auth and metadata in PostgreSQL. Uploads stream to disk in
1 MiB chunks. The dataset row and its ingest job are written in **one transaction**, and
a separate worker claims jobs with `SKIP LOCKED`. The worker reads the file with DuckDB,
infers and validates types, and writes zstd Parquet atomically. Queries never touch
PostgreSQL data. They run in pre-forked sandbox processes, each with a fresh in-memory
DuckDB that can only see the caller's Parquet files. Charts are declarative specs
compiled to one aggregate query, so the browser gets at most 5,000 points whatever the
dataset size. Diagrams: [`docs/architecture/overview.md`](architecture/overview.md).

## Difficult decisions

1. **Postgres queue rather than Redis or Celery** (ADR-0002). Transactional enqueue
   removes a whole class of bugs ("dataset with no job"). Leases and heartbeats give crash
   recovery. The trade-off is polling, which is fine at this volume.
2. **Re-rendering validated SQL** (ADR-0003). Passing the original string through after
   validating it leaves a gap between what was checked and what runs, for example
   comments, a trailing `;` or dialect quirks. Re-rendering the checked tree closes that
   gap. It also fixed a real bug: saved queries ending in a `--` comment broke when
   embedded as chart sources.
3. **A fresh DuckDB connection per query** (ADR-0003). This costs about 17 ms every time,
   but no state (temp tables, settings, cached views) can leak between users. Measuring
   it made the cost a number instead of a guess.
4. **Aggregating charts in SQL** (ADR-0004). This is why a 5M-row chart is one small
   response. Series fold into "Other", and NULLs get their own group. A screenshot review
   caught NULLs being silently folded into "Other", and that is now covered by a test.
5. **Signed download links** (ADR-0006). `fetch` with an auth header buffers the whole
   file in memory. A short-lived HMAC link lets the browser stream it.

## Questions to expect, with answers

- **How do you stop `SELECT * FROM read_csv('/etc/passwd')`?** The guard rejects the
  table function. Even if it didn't, DuckDB's `allowed_paths` contains only that
  dataset's Parquet files, external access is off, and the configuration is locked. A
  test calls the sandbox directly, skipping the guard, to prove the second layer holds.
- **What happens if a worker dies mid-ingest?** The lease expires after 60 s and another
  worker reclaims the job. The half-written `.tmp` Parquet file is never registered, and
  the attempts counter caps retries. After the last attempt, the dataset is marked
  failed with the error.
- **Why is API memory flat during a 438 MiB upload?** The body is read as a stream and
  written in 1 MiB chunks while being hashed. Nothing holds the whole file.
- **What limits throughput?** At 5M rows, `count(DISTINCT)` takes about 329 ms in DuckDB.
  Four sandboxes on 4 vCPUs gave 26 queries/s with no 503s at 8 clients. More throughput
  means more sandboxes and cores, or pre-aggregated rollups.
- **What would you change for production?** Real auth (OIDC), S3 storage behind the
  existing `Storage` interface, rate limiting, a script CSP with nonces, metrics, and
  dependency audits in CI.

## How the pieces work

- **Engine:** DuckDB 2.0 in-process, columnar and vectorised. It reads Parquet with
  projection and predicate pushdown, which is where the 427× one-column speed-up comes
  from.
- **Jobs:** a `jobs` table with `status`, `attempts`, `lease_expires_at`, `progress` and
  `error`. Workers poll every 0.5 s and claim with `FOR UPDATE SKIP LOCKED`. Heartbeats
  run on a thread every ≤15 s. Job kinds: ingest, profile, materialize (transforms),
  export.
- **Storage:** immutable, versioned files under `raw/`, `processed/` and `exports/`, all
  behind a `Storage` interface that refuses keys escaping its root. Metadata lives in
  PostgreSQL, managed with Alembic migrations.
